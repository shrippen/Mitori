Lehrgangsmodus · zum Weiterdenken

Notizen von Lehrgängen, die nicht im Programm stehen

Auf Lehrgängen wird fast nie Prüfungsstoff gezeigt. Gebraucht wird daher vor allem ein schnelles Notizfeld, das den Lehrgang kennt und Fachwörter richtig schreibt. Drei Ansätze, die sich kombinieren lassen:

1 · Lehrgang als Notizbuch

  • Lehrgang aus dem Kalender wählen (ICS, siehe unten): Titel, Ort, Lehrer und Datum sind schon da.
  • Eine Seite je Lehrgang, freie Einträge untereinander, jeder mit Uhrzeit (Samstag 11:15 …).
  • Einfach, schnell auf der Matte; später gut zu durchsuchen.

2 · Einträge mit Struktur, wo sie leicht ist

  • Jeder Eintrag kann optional Angriff, Technik und Waffe tragen; Autovervollständigung aus dem Glossar, auch für Begriffe ohne Programmbezug.
  • Passt ein Eintrag zu einer Programmtechnik, lässt er sich verknüpfen: die Notiz erscheint dann auch dort.
  • Suche „alles mit Kote-gaeshi“ findet Programm und Lehrgänge.

3 · Festhalten ohne Tippen

  • Foto oder Skizze (Fußstellung, Ablauf) an einen Eintrag hängen.
  • Sprachnotiz im Pausengespräch, nur auf dem Gerät gespeichert.
  • Export der Lehrgangsseite als Markdown oder PDF, z. B. als Grundlage für einen Bericht in der Shinki News.

Offene Fragen

  • offenLehrgänge auch ohne Kalendereintrag anlegen (private Trainings, Gastlehrer)?
  • offenFotos und Sprachnotizen ja oder nein? (Speicherplatz, Einverständnis der Gezeigten)
  • offenNotizen mit anderen Teilnehmern teilen, oder bleiben sie privat?
  • offenSollen Lehrgangsnotizen im „Wiederholen nach Plan“ auftauchen?
Videos

Video-Bundles mit Freischaltcode

Die Videos sind nicht in der App. Der Verband verkauft die DVDs und verschickt dazu einen Code; mit dem Code lädt Mitori das passende Bundle nach. Jedes Bundle bringt seinen Katalog (Techniken, Kapitelzeiten) selbst mit, die App braucht keine weiteren Metadaten über die Dateien.

Sicherheitskonzept: kein Geheimnis in der App

Ein kurzes gemeinsames Passwort ließe sich ausprobieren oder aus der App lesen. Darum bekommt jede DVD einen eigenen, langen Zufallscode, und nur dieser Code öffnet den Schlüssel des Bundles.

1 · Du bereitest vor (einmal je Bundle)

Inhaltsschlüssel erzeugenzufällig, 256 Bit, je Bundle einer
Bundle verschlüsselnVideos + katalog.json, AES-256 in Blöcken (Spulen bleibt möglich)
Hochladenauf eigenen Server oder als generisches Gitea-Paket; verschlüsselt darf es öffentlich liegen (1,6 GB, nicht GitHub)

2 · Je verkaufter DVD

Code erzeugen20 Zeichen Crockford-Base32 ≈ 100 Bit, z. B. 7KQ2M-X9HDV-3TAPR-WE6YC
Schlüssel umhüllenInhaltsschlüssel mit Argon2id(Code) verschlüsselt
Manifest ergänzenEintrag: Lookup-Id = Hash(Code), umhüllter Schlüssel, Bundle-Name; verrät den Code nicht
Code verschickenmit der DVD oder per Mail; der Code ist das einzige Geheimnis

Warum Ausprobieren nicht hilft

  • Die App enthält weder Codes noch Schlüssel; wer sie zerlegt, findet nichts.
  • Wer Manifest und Bundle kopiert, muss den Code raten: 2100 Möglichkeiten, jede mit einer absichtlich langsamen Argon2id-Rechnung. Das ist auch mit viel Rechenleistung aussichtslos.
  • Ein Code gilt nur für sein Bundle. Ein weitergegebener Code lässt sich im Manifest sperren; wer das Bundle schon geladen hat, behält es.

Alternative: Server prüft den Code

  • Ein kleiner Dienst nimmt den Code entgegen, begrenzt Versuche je Adresse und gibt einen zeitlich gültigen Download-Link heraus.
  • Vorteil: Sperren und Zählen der Aktivierungen wirken sofort; kurze Codes wären möglich.
  • Nachteil: ein Dienst, der laufen und gepflegt werden muss. Empfehlung: das Manifest-Verfahren oben, es braucht nur statische Dateien.

Was kein Verfahren verhindert

  • Nach dem Entschlüsseln liegen die Videos auf dem Gerät und lassen sich kopieren.
  • Option mit mehr Aufwand: Videos bleiben verschlüsselt gespeichert und werden erst beim Abspielen entschlüsselt (eigenes QIODevice mit AES-CTR, damit Spulen geht). Erschwert Kopieren, verhindert es nicht.

Werkzeug für dich

  • tools/bundle.py build aikido-kyu Aikido/Kyu*.mkv: verschlüsselt, schreibt Katalog und Prüfsummen.
  • tools/bundle.py codes aikido-kyu --anzahl 50: erzeugt Codes als CSV für den Verband und ergänzt das Manifest.
  • tools/bundle.py sperren <Code>: entfernt den Eintrag aus dem Manifest.
Technik

Qt 6 + Kirigami wie Plasmai: eine Codebasis für Android und Plasma Mobile

Bausteine

  • Oberfläche: QML mit Kirigami, Kante-QML-Modul unverändert; Theme „Shinki“ als zweiter Satz Rollen in Kante.
  • Video: QtMultimedia MediaPlayer, playbackRate 0,25–1 (Ton aus), Schleife über die Kapitelgrenzen, Einzelbild = 40 ms bei 25 fps. HEVC dekodiert Android in Hardware, Plasma Mobile über das FFmpeg-Backend.
  • Daten: Programmdaten aus Teil a als JSON im Paket (dieselbe Quelle wie das LaTeX-Heft). Kapitelzeiten kommen mit dem Bundle. Übungsprotokoll, Notizen und Bewertungen in SQLite.
  • Glossar-Aussprache: vorgenerierte Schnipsel als Opus-Dateien (je 5–15 KB) im Paket. Entweder einmalig mit einer japanischen Sprachsynthese erzeugt und angehört, oder besser vom Sensei eingesprochen.
  • Termine: https://cal.arianw.de/dav/calendars/shinki/Lehrgaenge?export liefert ohne Anmeldung ein ICS (geprüft 01.11.2026). Nur HTTPS verwenden: die HTTP-Adresse leitet um, und Android blockiert Klartext-HTTP ohnehin.
  • Bildschirm wach halten: Android FLAG_KEEP_SCREEN_ON, Plasma Mobile org.freedesktop.ScreenSaver.Inhibit.

Aus Plasmai übernommen

Update-Check wie in Plasmai

Plasmai nutzt die Kante-Komponente KanteUpdateCheck (QML, ohne Oberfläche). Sie fragt höchstens einmal am Tag https://shrippen.github.io/versions.json per einfachem GET ab, vergleicht mit der installierten Version und meldet available, latestVersion, latestUrl. Sie lädt nichts herunter; den Hinweis zeigt die App selbst (Karte im Menü, siehe Variante 3). Fehler bleiben still, eine verworfene Version wird gemerkt.

Für Mitori: project: "mitori" in overview/sites.json eintragen, build-versions.py nach jedem Release, Antwort in den Einstellungen speichern (memory), im Demo-Modus aus. In F-Droid- oder Flathub-Builds später abschalten, dort aktualisiert der Store.

Veröffentlichung

Releases zuerst nur über GitHub

Ablauf

  1. Repo auf Gitea (origin), Push-Mirror nach GitHub.
  2. CI auf GitHub (checks.yml: Arch-Container, Tests, qmllint, release-notes.sh --check), Status github / test an Gitea; auf Gitea nur pr-agent.yml.
  3. Tag auf Gitea, GitHub baut und hängt an: signierte APK, Flatpak-Bundle für Plasma Mobile, AppImage.
  4. Landing Page mit Kante, Changelog Deutsch/Englisch, Screenshots aus dem Demo-Modus.
  5. Später, wenn gewünscht: F-Droid, Flathub.

Was nie ins Repo kommt

  • Videos, unverschlüsselt oder verschlüsselt.
  • Inhaltsschlüssel und Codes; tools/bundle.py legt sie in einem Ordner außerhalb des Repos ab.
  • Ob Programmdaten (Technik-Namen) öffentlich sein dürfen, entscheidet der Verband; sonst bleibt das Repo privat.

Offene Themen

Sicherung

Muss möglich sein, Verfahren noch offen. Optionen:

  • Datei-Export/-Import (SQLite oder JSON) über den Android-Dateidialog: einfach, manuell.
  • Android Auto Backup in das Google-Konto: unsichtbar, aber nur Android und nicht auf jedem Gerät.
  • WebDAV/Nextcloud: automatischer Abgleich mit eigenem Server, auch für Plasma Mobile.
  • Syncthing-Ordner: App schreibt regelmäßig eine Sicherungsdatei, Syncthing verteilt sie.

Videos

  • Bundles neu kodieren (z. B. kleiner für Telefone) oder Originaldateien?
  • Verschlüsselt auf dem Gerät lassen (siehe oben) oder nach dem Laden entschlüsseln?
  • Hosting: eigener Server oder Gitea-Paket; Kosten und Bandbreite bei vielen Downloads.
  • Zustimmung des Verbands zum Verfahren und zum Codeversand.
